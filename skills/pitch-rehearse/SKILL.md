# 발표 준비 (pitch-rehearse)

## 목적

**덱이 좋다고 발표가 좋은 게 아니다.**

슬라이드는 완벽한데 무슨 말을 할지 몰라 읽기만 하는 팀, 질문 하나에 무너지는 팀 — 매번 나온다. 여기서 **말할 내용·시간·질문 대응**을 준비하고 **실제로 소리 내어 연습한다.**

> `demo-script`가 **화면을 어떻게 보여줄지**였다면, 여기는 **발표 전체를 어떻게 끌고 갈지**다.

## 시작 전

`context.md`에서 **문제·데이터 근거·솔루션·핵심 기능**을, 산출물에서 **pitch-deck.html · demo-script.md**를 읽는다. 덱이 없으면 `$pitch-deck-build` 먼저.

컬러 역할: 🔴Red(결론·총괄) 🔵Blue(데이터·질문 방어) 🟢Green(사용자·스토리) 🟡Yellow(전달·대본).

---

## ① 발표 시간 배분 — 먼저 정한다

*"발표 시간이 몇 분이에요?"* (모르면 FT에게 확인)

**7분 기준 배분** (시간이 다르면 비율로 조정):

| 구간 | 시간 | 무엇 |
|---|---|---|
| 문제 | 1분 30초 | 누가, 무슨 불편을 겪나 |
| **데이터 근거** | 1분 30초 | 그게 진짜인 이유 ← **여기가 우리 강점이다** |
| 솔루션 | 1분 | 그래서 뭘 만들었나 |
| **데모** | 1분 30초 | `demo-script.md` 그대로 |
| 임팩트·다음 | 1분 | 이게 있으면 뭐가 달라지나 |
| 여유 | 30초 | 반드시 남겨둔다 |

**데모에 시간을 몰아주고 싶은 유혹을 참는다.** 데이터 근거가 이 부트캠프의 채점 포인트다.

---

## ② 슬라이드별 대본 — 🟡 Yellow

**슬라이드를 읽지 않는다.** 슬라이드에 없는 말을 한다.

| 슬라이드 | 화면에 있는 것 | **말할 것** (슬라이드에 없는) | 초 |
|---|---|---|---|
| 표지 | 제목 | *"금요일 밤 9시, 통영. 여행자는 편의점에 있습니다."* | 15 |
| 문제 | 문제 한 줄 | 페르소나 이야기, 왜 이게 문제인지 | 60 |
| 데이터 | 차트 | *"숙박 비중은 상위인데 소비는 하위. 자고는 가는데 돈을 안 씁니다."* | 90 |
| … | | | |

**대본 쓰는 규칙:**
- **한 슬라이드 = 한 메시지 = 세 문장 이내.** 길면 못 외운다.
- **숫자는 정확히 외운다.** *"소비지수 65점, 전국 하위 20%"* — 얼버무리면 신뢰가 깨진다.
- **문어체 금지.** 쓴 대로 말하면 어색하다. **소리 내어 읽어보고** 안 넘어가는 문장은 고친다.
- 첫 문장과 마지막 문장만은 **토씨까지 외운다.** 나머지는 흐름만 알면 된다.

---

## ③ 예상 질문 — 🔵 Blue ★ 여기서 승부가 갈린다

**심사위원은 반드시 묻는다.** 준비 안 하면 그 자리에서 무너진다.

### 거의 항상 나오는 질문

| 질문 | 준비할 답의 뼈대 |
|---|---|
| **"이거 진짜 되는 거예요?"** | 지금 되는 것 / 목업인 것 / 실서비스에 필요한 것을 **솔직히 구분해서** 말한다. 숨기면 걸린다. |
| **"데이터 근거가 뭐예요?"** | 출처·지표·수치를 정확히. *"관광공사 수요강도 지수, 통영 숙박비중 87.9 vs 소비 65.3"* |
| **"기존에 있는 서비스 아니에요?"** | 뭐가 다른지 **한 문장**. 없으면 지금 만든다. |
| **"왜 이 지역이에요?"** | 데이터로 답한다. "관심 있어서"는 감점. |
| **"누가 돈을 내요?"** | 지자체 / 관광공사 / 사업자 중 누구에게 무슨 가치인지. |
| **"이 숫자, 상대 지수인데 절대값처럼 말한 거 아니에요?"** | ⚠**우리 데이터의 약점을 심사위원이 먼저 짚을 수 있다.** 지수는 지역 간 비교용임을 알고 있다고 말한다. |

### 우리 프로젝트만의 질문 — 팀이 찾는다

*"우리 발표에서 제일 약한 데가 어디예요? 제가 심사위원이면 거기를 물어볼 텐데."*

**팀이 직접 3개를 뽑고 답을 만든다.** AI가 대신 뽑아주지 않는다 — 자기 약점은 자기가 제일 잘 안다.

### 답변 3원칙

1. **모르면 모른다고 한다.** *"그건 확인 못 했습니다. 다음 단계로 보고 있습니다."* — 아는 척하다 걸리는 게 최악이다.
2. **한계를 먼저 말해버린다.** *"지금은 데이터를 미리 받아 넣었고, 실서비스에선 서버가 매일 갱신합니다."* → 판단할 줄 아는 팀이라는 신호.
3. **30초 안에 끝낸다.** 길어지면 방어처럼 들린다.

---

## ④ 리허설 — 실제로 한다 ★

**대본 쓰고 끝내면 아무 소용 없다.**

1. **타이머 켜고 처음부터 끝까지.** 실제로 소리 내어.
2. *"몇 분 나왔어요?"* — 넘으면 **내용을 줄인다.** 빨리 말하는 걸로 해결하려 하지 마라.
3. **다른 팀에게 보여주고 질문을 받는다.** *"뭐가 이해 안 됐어요? 뭘 물어보고 싶어요?"* ← 여기서 나온 질문이 진짜 예상 질문이다.
4. 고치고 **한 번 더.**

> **최소 2번.** 첫 번째는 반드시 버벅인다. 세 번째부터 사람 말처럼 들린다.

**발표자를 정한다.** 전원이 한마디씩 할 필요 없다 — 매끄러운 1~2명이 낫다. 대신 **Q&A는 담당별로 나눠 받는다**(데이터 질문은 Blue, 사용자 질문은 Green).

## 끝맺음

- *"자, 이제 무대에서 뭘 말할지 다 정해졌어요. 남은 건 한 번 더 돌려보는 것뿐이에요."*
- 시간이 남으면:
  - *"제일 무서운 질문 하나만 더 만들어볼까요? 그거 준비되면 나머진 다 쉬워요."*
  - *"첫 문장, 다시 한번 들려주세요. 그거 하나로 심사위원이 들을지 말지 정해요."*
  - *"발표 끝나고 심사위원 머릿속에 딱 한 문장이 남는다면 뭐였으면 좋겠어요?"*

## 톤

- **연습을 시킨다.** 정리하고 끝내지 말고 **타이머 켜고 소리 내어** 하게 한다.
- 질문 준비를 겁주기로 만들지 않는다. *"질문이 나온다는 건 관심이 있다는 뜻이에요."*
- 완벽주의를 경계한다. *"안 떨 순 없어요. 끊기지만 않으면 돼요."*
