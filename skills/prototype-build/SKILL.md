# 6단계 · 프로토타이핑 (prototype-build)

## 목적
솔루션 MVP를 **실제로 클릭되는 데모**(`prototype.html`)로 만들고, **Codex Sites에 배포해 URL까지** 만든다. 파일을 여는 것과 "우리 서비스 주소"를 띄우는 것은 발표에서 무게가 다르다 — 심사위원과 다른 팀이 자기 폰으로 열어볼 수 있다. 발표 덱은 이 스킬이 아니라 **`pitch-deck-build`** 담당. 오피스아워 피드백으로 **여러 번 반복**한다.

## 진행 순서 (한눈에)
만들기 → 반복 → **배포(전 팀 종착점)** → 시간 남으면 다음 계단(선택).

## 시작 전
> ⚠ **`$idea-validate`를 먼저 거쳤나?** 핵심 기능이 1개로 좁혀지고 🔴 위험이 정리돼 있어야 한다. 안 했으면 지금이라도 하고 오는 게 빠르다.
- `context.md`의 `주제`·`지역`·`데이터 검증 요약`·**`MVP 정의`(idea-validate 확정본 + 오피스아워 메모)** 를 읽는다. **정의서에 없는 기능을 만들자는 말이 나오면 "그럼 정의서부터 고치자"로 되돌린다** — 정의서가 계약이다.
- 4단계에서 받은 실제 수치·장소명을 최대한 넣는다. 없으면 현실적인 예시값 + "예시" 표기.
- **디자인은 이미 정해져 있다.** `design.md`(`$design-setup` 산출물)의 CSS 토큰을 그대로 쓴다. 없으면 `$design-setup` 먼저 — 만들면서 색 고민하지 않는다.

## 먼저 묻기 (필수 — 퍼실리테이션)
바로 코드를 뽑지 말고 **화면의 내용**을 팀에게서 끌어낸다. **디자인(색·무드)은 묻지 않는다 — 이미 `design.md`에 있다.**
1. *"사용자가 이 화면을 처음 열면 뭐가 보여야 해요?"* — 첫 화면에 뭘 놓을지.
2. *"뭘 입력하고, 뭘 누르면, 뭐가 나오나요?"* — 입력 → 처리 → 출력을 팀 말로.
3. **꼭 보여줄 핵심 기능 1개**를 팀이 짚게(`idea-validate`에서 좁힌 것과 일치 확인).
4. *"우리가 찾은 데이터 중에 화면 어디에 올려야 문제가 한눈에 보일까요?"*
답·합의는 `context.md`에 남긴다.

## 산출 규칙 (중요)
- **단일 파일 HTML**: HTML+CSS+JS 한 파일. 외부는 CDN만. **localStorage 등 브라우저 저장소 금지** — 상태는 JS 변수/메모리.
- 모바일에서도 보이게 반응형. 한국어 UI. (배포하면 심사위원이 폰으로 연다 — 반응형이 실전이 된다.)
- 데이터는 파일 안에 JS 객체로 넣어 **오프라인에서도 데모**되게. 이 원칙 덕에 배포가 실패해도 발표는 멈추지 않는다.
- **API 키를 HTML에 절대 넣지 않는다** — 배포하는 순간 전 세계에 공개된다.

## prototype.html 만들기
- MVP 흐름(입력→처리→출력)을 **실제로 클릭되는** 화면으로. 최소 1개 핵심 기능이 동작.
- 예: 관심사 선택 → (내장 데이터로) 코스 생성 → 지도/카드 출력.
- 과욕 금지: 발표에서 보여줄 **1~2 기능만 완성도 있게.**

## 실제 데이터 넣기 (TourAPI·혼잡도)
실제 수치·장소·혼잡도 예보를 화면에 올리고 싶으면 **반드시 `references/실데이터-인라인.md`를 읽고 그대로** 한다. 브라우저에서 API를 직접 부르면 CORS로 무조건 실패한다 — 정해진 우회로(터미널 1회 호출 → HTML에 인라인)가 있고, 이 방식이 발표장에서 가장 안전하다.

## 반복 (충분히 다듬기)
- 오피스아워·팀 피드백을 받으면 *"어디를 바꾸고 싶어요?"* 로 받아 **해당 부분만** 수정(전면 재작성 지양).
- 매 반복 후 `context.md` 로그에 "vN: 무엇을 고침" 기록.
- **사용자 테스트**: 다른 팀·주변 사람에게 눌러보게 하고 *"어디서 헷갈렸어요?"* → 반영(`$deep-dive` 연계).
- **시연 예행**: 발표에서 보여줄 클릭 순서를 지금 한 번 밟아본다. 결과가 밋밋하거나 클릭이 너무 많으면 **지금** 고친다 — 피칭 준비 단계에서 발견하면 늦다.

## 배포 — Codex Sites (전 팀의 종착점)
핵심 기능 1개가 로컬에서 확실히 돌면 배포한다. **완벽해질 때까지 미루지 말 것** — 배포는 반복 중에 몇 번이고 다시 할 수 있고, 일찍 URL을 만들어두면 피드백 받기도 쉬워진다.
- 절차는 `references/sites-배포.md`를 읽고 따른다.
- 배포되면 **팀 전원이 자기 폰으로 URL을 열어** 확인한다(반응형·데이터 표시·깨진 곳).
- URL을 `context.md`에 기록하고 발표 덱에 넣는다.
- 배포가 막히면 붙잡고 있지 말 것: **로컬 더블클릭 데모가 폴백**이다(우리 파일은 오프라인에서도 열리게 만들었다). FT를 부르고, 발표 준비는 계속 간다.

## 더 가고 싶은 팀에게 (선택 — 다음 계단)
여기까지가 이 스킬의 기본 트랙이다. 배포까지 끝났고 시간이 남으면, `references/업그레이드-경로.md`에 다음 계단이 있다 — 실데이터를 더 깊게(L2), 대화형 에이전트로(L3). **시작 전에 FT에게 "업그레이드 해보고 싶다"고 말하라** — 남은 시간 대비 어디까지가 현실적인지 같이 잡아준다.

## context.md 갱신
- `산출물`에 `prototype.html` 경로 + **배포 URL**.
- `단계: 6`, 로그 추가.

## 끝맺음 (여기까지가 4단계: 프로토타입)
- 요약: 파일 경로 + 배포 URL + 핵심 기능 한 줄.
- **다음은 `$pitch-deck-build`** — 이 화면을 감싸는 발표 덱을 만든다. 이어서 `$pitch-prep`에서 시연 시나리오·대본·리허설까지 피칭 전체를 준비한다. 만든 것과 보여주는 것은 다른 일이다.
- 아직 안 열렸으면 재촉하지 말고 팀과 나눈다:
  - *"이 데모, 처음 보는 사람이 눌러도 30초 안에 '오' 할까요? 어디가 약해요?"*
  - *"발표 때 이 화면으로 어떤 이야기를 할지 미리 말로 해볼까요?"*

## 톤·품질
- 완성도 > 기능 수. 하나라도 확실히 되는 데모, 그리고 그 데모의 URL.
