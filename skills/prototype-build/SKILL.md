# 6단계 · 프로토타이핑 (prototype-build)

## 목적
솔루션 MVP를 **실제로 클릭되는 데모**(`prototype.html`)로 만든다. 발표 덱은 이 스킬이 아니라 **`pitch-deck-build`** 가 담당한다. 오피스아워 피드백으로 **여러 번 반복**한다(2박3일 동안 충분히 다듬는다).

## 시작 전
> ⚠ **`$idea-validate`를 먼저 거쳤나?** 핵심 기능이 1개로 좁혀지고 🔴 위험이 정리돼 있어야 한다. 안 했으면 지금이라도 하고 오는 게 빠르다.
- `context.md`의 `주제`·`지역`·`데이터 검증 요약`·`아이디어`(사용자·시나리오·MVP)를 읽는다.
- 4단계에서 받은 실제 수치·장소명을 최대한 넣는다. 없으면 현실적인 예시값 + "예시" 표기.
- **디자인은 이미 정해져 있다.** `design.md`(`$design-setup` 산출물)의 CSS 토큰을 그대로 가져다 쓴다. 없으면 `$design-setup` 먼저 — 만들면서 색 고민하지 않는다.

## 먼저 묻기 (필수 — 퍼실리테이션)
바로 코드를 뽑지 말고 **화면의 내용**을 팀에게서 끌어낸다. **디자인(색·무드)은 묻지 않는다 — 이미 `design.md`에 있다.**
1. *"사용자가 이 화면을 처음 열면 뭐가 보여야 해요?"* — 첫 화면에 뭘 놓을지.
2. *"뭘 입력하고, 뭘 누르면, 뭐가 나오나요?"* — 입력 → 처리 → 출력을 팀 말로.
3. **꼭 보여줄 핵심 기능 1개**를 팀이 짚게(`idea-validate`에서 좁힌 것과 일치 확인).
4. *"우리가 찾은 데이터 중에 화면 어디에 올려야 문제가 한눈에 보일까요?"*
답·합의는 `context.md`에 남긴다.

## 산출 규칙 (중요)
- **단일 파일 HTML**: HTML+CSS+JS 한 파일. 외부는 CDN만. **localStorage 등 브라우저 저장소 금지** — 상태는 JS 변수/메모리.
- 모바일에서도 보이게 반응형. 한국어 UI.
- 데이터는 파일 안에 JS 객체로 넣어 **오프라인에서도 데모**되게(발표장 네트워크 대비).

## prototype.html
- MVP 흐름(입력→처리→출력)을 **실제로 클릭되는** 화면으로. 최소 1개 핵심 기능이 동작.
- 예: 관심사 선택 → (내장 데이터로) 코스 생성 → 지도/카드 출력.
- 과욕 금지: 발표에서 보여줄 **1~2 기능만 완성도 있게.**

## 반복 (충분히 다듬기)
- 오피스아워·팀 피드백을 받으면 *"어디를 바꾸고 싶어요?"* 로 받아 **해당 부분만** 수정(전면 재작성 지양).
- 매 반복 후 `context.md` 로그에 "vN: 무엇을 고침" 기록. 시간이 남으면 실데이터·인터랙션·완성도를 계속 올린다.

## 심화 (시간 있으면 — 2박3일 깊이)
- **사용자 테스트**: 다른 팀·주변 사람에게 실제로 눌러보게 하고 *"어디서 헷갈렸어요?"* → 반영. (`field-research`와 연계)
- **실데이터 확장**: TourAPI에서 더 많은 장소·카테고리를 받아 데모를 풍부하게.
- **혼잡도 붙이기** (쏠림·계절·분산·코스 주제라면 강력 추천): 집중률 API는 **호출한 날부터 30일치 예보**를 준다 → *"이번 주말 여긴 붐빔(98), 대신 여기 어때요(41)"* 를 화면에 그대로 띄울 수 있다. 데모가 확 산다.

  ### ⚠ 브라우저에서 TourAPI를 직접 부르면 안 된다 (CORS)
  `apis.data.go.kr`은 CORS 헤더를 주지 않는다. **HTML에서 fetch하면 무조건 실패한다** — 로컬에서 열든, 메타앱에 올리든 똑같다. 키를 HTML에 박는 것도 금물(업로드하면 다른 팀에 그대로 노출된다).

  ### 대신: 데이터를 HTML 안에 박는다 (이게 정답이다)
  1. **터미널에서 한 번** 호출한다(키는 `.env`에만 남는다).
     ```bash
     curl -s "https://apis.data.go.kr/B551011/TatsCnctrRateService/tatsCnctrRatedList?serviceKey=$DATA_GO_KR_SERVICE_KEY&numOfRows=1000&pageNo=1&MobileOS=ETC&MobileApp=ftskill&_type=json&areaCd={행정시도}&signguCd={행정시군구}"
     ```
     ⚠ `baseYm`을 넣으면 에러다. 응답: `tAtsNm`·`baseYmd`·`cnctrRate`(100=가장 붐빌 때).
  2. 받은 값을 **`prototype.html` 스크립트 안에 `const DATA = [...]` 로 인라인**한다.
     > **별도 `data.json` 파일을 두지 마라.** `file://`로 열면 로컬 JSON을 fetch하는 것도 CORS로 막힌다(origin `null`). 로컬 서버를 띄워야 하는데, 발표 자리에서 그럴 이유가 없다. **파일 하나, 더블클릭이면 열린다** — 우리 단일 파일 원칙과도 맞는다.
  3. 30일 예보라 **부트캠프 3일 내내, 심사 시점에도 유효하다.** 실시간처럼 보이고 실제로도 맞다.
  - 공급 데이터(관광지·음식·숙박 목록)도 같은 방식으로 받아 인라인한다.
  - 팀에 물어라: *"어떤 데이터를 화면에 올려야 우리 주장이 한눈에 보일까요?"*

  ### 피칭 때 한 줄 (심사위원이 좋아한다)
  *"지금은 받아둔 데이터를 넣어 보여드리지만, 실서비스에선 **서버가 API를 대신 호출**해 매일 갱신합니다."*
  → 정적 데이터는 '진짜 앱의 방식'이 아니라 **서버 없이 데모를 만드는 우회로**다. 이 한계를 팀이 알고 말하면 신뢰가 올라간다.
- **완성도 올리기**: 반응형·빈 상태·로딩·마이크로 인터랙션·접근성(대비·글자 크기).
- **2~3차 iteration**: 오피스아워 사이에 계속 다듬는다(한 번에 끝내지 않는다).

## context.md 갱신
- `산출물`에 `prototype.html` 경로.
- `단계: 6`, 로그 추가.

## 끝맺음 (여기까지가 4단계: 프로토타입)
- 요약: 파일 경로 + 핵심 기능 한 줄.
- **다음은 `$demo-script`** — 무대에서 이 화면을 **어떤 순서로, 누가, 뭐라고 말하며** 보여줄지 짜고 실제로 리허설한다. 만든 것과 보여주는 것은 다른 일이다.
- **서두르지 않는다.** 넘어가기 전에 팀과 아래를 더 나눠도 좋다:
  - *"이 데모, 처음 보는 사람이 눌러도 30초 안에 '오' 할까요? 어디가 약해요?"*
  - *"다른 팀·주변 사람한테 한번 눌러보게 하고 반응을 볼까요?"* (`$field-research`)
  - *"발표 때 이 화면으로 어떤 이야기를 할지 미리 말로 해볼까요?"*
  - 시간 남으면 실데이터·완성도를 더 올린다(위 '심화').

## 톤·품질
- 완성도 > 기능 수. 하나라도 확실히 되는 데모.
