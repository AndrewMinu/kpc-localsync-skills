# Codex Sites 공개 배포 절차 — 정적 보존과 동적 앱

> `prototype-build`의 배포 참고 문서. 참가자는 명령어·호스팅 계정·도메인을 따로 설정하지 않는다. 캠프 발표용 Sites는 `public`으로 게시하고, 로그인 없는 핵심 데모와 팀 휴대폰 동작까지 확인한다.

## 먼저 배포 방식을 고른다

| 방식 | 이 방식을 고르는 때 | 배포 원본 | `prototype.html`의 역할 |
|---|---|---|---|
| **정적 원본 보존**(기본) | 현재 핵심 기능이 단일 HTML에서 작동하고 공개 URL만 필요 | `prototype.html` | 구현 원본 + 오프라인 폴백 |
| **동적 앱** | 인증·DB·서버 API·업로드·실시간 협업 등 정적 HTML로 검증할 수 없는 기능이 MVP에 있거나, 팀이 제품형 구현을 명시적으로 선택 | `site/` 앱 소스 | 배포 전 기준선 + 오프라인 폴백 |

**React/Next 계열 화면을 쓰고 싶은 것 자체가 문제는 아니다.** Sites에 올리기 위한 기술적 이유만으로 이미 작동하는 화면을 다시 만드는 것은 피한다. 반대로 합의한 MVP가 동적 기능을 요구하면 원본 보존 규칙을 이유로 구현을 막지 않는다. 새 동적 사이트는 Sites가 지원하는 `vinext/React` 구조를 기본으로 하고, 기존 사이트는 작동하는 호환 구조를 보존한다.

## 모든 방식의 공통 계약

1. **공개 범위:** 캠프 발표용 접근 범위는 `public`이다. ChatGPT 로그인이나 워크스페이스 가입을 요구하는 주소는 완료가 아니다.
2. **공개 데모:** 서비스 자체에 회원 기능이 있어도 심사위원이 가입 없이 핵심 기능을 체험할 수 있는 공개 데모 경로를 둔다.
3. **같은 주소 재사용:** `site/.openai/hosting.json`의 `project_id`를 보존하고 같은 사이트에 새 버전으로 배포한다. 수정할 때 새 사이트를 만들지 않는다.
4. **비밀 금지:** API 키·`.env`·개인정보를 HTML·브라우저 번들·공개 저장소에 넣지 않는다. 동적 앱은 Sites의 서버 쪽 비밀 설정과 서버 경로를 쓴다.
5. **기준선 보존:** `prototype.html`을 삭제하거나 배포 산출물로 덮어쓰지 않는다. 정적 방식은 바이트 일치를, 동적 방식은 아래 제품 계약을 확인한다.

## 배포 전 체크

- [ ] `prototype.html`이 더블클릭으로 열린다. 정적 방식은 핵심 기능 1개가 실제로 동작하고, 동적 방식은 예시 데이터로 핵심 입력→결과 기준선이 동작한다.
- [ ] 배포 방식을 `정적 원본 보존` 또는 `동적 앱`으로 정했다.
- [ ] 요청이나 `MVP 정의`가 이미 방식을 정했다면 선택 질문을 되풀이하지 않고 이유만 기록했다.
- [ ] 공개 파일·브라우저 코드에 API 키·`serviceKey` 값·환경변수 값이 없다.
- [ ] 팀 이름 외에 공개하면 안 되는 개인정보가 없다.
- [ ] 기존 `site/.openai/hosting.json`이 있으면 보존했다.

하나라도 실패하면 배포하지 말고 먼저 해결한다.

## A. 정적 원본 보존 방식

참가자가 이렇게 요청하면 된다.

> `prototype.html을 내용과 동작을 바꾸지 말고 Codex Sites에 공개 배포해줘. 로그인 없는 접근과 휴대폰 화면까지 확인하고 API 키는 포함하지 마.`

1. 사용 가능한 `sites-building`으로 최소 `site/` 포장 프로젝트를 준비하고, 검증 뒤 `sites-hosting`으로 게시한다.
2. `site/public/prototype.html`을 기준선 `prototype.html`의 바이트 단위 복사본으로 만든다.
3. Sites용 최소 셸의 `/`는 `/prototype.html`로 연결만 한다. 셸은 배포를 위한 구조일 뿐, 화면을 React/Next 계열로 옮겨 쓰거나 새 UI를 만들지 않는다.
4. 복사 뒤 `cmp` 또는 SHA-256으로 두 파일이 같은지 확인한다. 다르면 게시하지 않는다.
5. 아래 **공개 게시와 검증**으로 간다.

정적 방식에서 수정할 파일은 기준선 `prototype.html`이다. 배포용 복사본을 직접 고치지 않는다.

## B. 동적 앱 방식

참가자가 이렇게 요청하면 된다.

> `이 MVP는 [필요한 동적 기능]이 핵심이야. prototype.html은 기준선과 오프라인 폴백으로 보존하고, 제품 계약을 유지하는 동적 앱으로 Codex Sites에 공개 배포해줘. 가입 없는 데모 경로와 휴대폰 화면까지 확인하고 비밀키는 서버에서만 사용해줘.`

1. **전환 이유를 확인한다.** 정적 HTML로 검증할 수 없는 기능 또는 팀이 합의한 제품형 구현 목표를 `context.md`의 `산출물 > 배포 > 동적 전환 이유`에 적는다.
2. **기준선을 보존한다.** 현재 경로는 `산출물 > 프로토타입`, 해시는 `산출물 > 배포 > 기준선 SHA-256`에 기록하고 `prototype.html`을 덮어쓰지 않는다.
3. **제품 계약을 읽는다.** `context.md`의 대상 사용자·문제·핵심 기능·데이터 근거와 `design.md`를 기준으로 `site/` 앱을 만든다. 새 사이트는 Sites의 `vinext/React` 구조를 쓰고, 기존 사이트는 Cloudflare Worker 호환 빌드 구조를 보존한다. 프레임워크를 바꾸는 일이 목표가 되지 않게 한다.
4. **불필요한 재설계를 피한다.** 아래 항목은 기본적으로 기준선과 같게 유지한다.
   - 대상 사용자와 해결하려는 문제
   - 핵심 기능 1개와 입력→출력 흐름
   - 데이터의 의미·출처·한계
   - 핵심 문구와 `design.md` 토큰
5. **차이는 의도적으로 관리한다.** 동적 기능에 필요한 변경이나 팀이 사용자 피드백으로 합의한 개선은 허용한다. 변경 이유와 영향을 `context.md`의 `산출물 > 배포 > 의도된 차이`에 적는다. 정의서 밖 기능을 몰래 늘리지 않는다.
6. **서버 경계를 지킨다.** 외부 API 키와 비밀값은 Sites의 서버 쪽 설정에 두고 서버 경로에서만 쓴다. 브라우저에는 필요한 결과만 내려준다. 공개 데모가 외부 API 실패로 멈추지 않도록 검증된 스냅샷 폴백을 둔다.
7. **기능을 검증한다.** 빌드 후 기준선의 핵심 입력→결과가 유지되는지, 합의한 동적 기능이 실제로 동작하는지 확인한다.
8. 아래 **공개 게시와 검증**으로 간다.

동적 방식에서 수정할 원본은 `site/`의 앱 소스다. 생성된 빌드 파일을 직접 고치지 않는다. `prototype.html`을 업데이트할 필요가 생기면 자동 동기화하지 말고, 팀과 합의해 새 기준선으로 갱신한 뒤 경로·해시·차이 기록을 함께 바꾼다.

## 공개 게시와 검증 — 두 방식 공통

1. **Sites 기능 확인**
   - `sites-building`으로 빌드·로컬 검증을 마친 뒤 `sites-hosting`으로 게시한다.
   - Sites 기능이 보이지 않거나 조직 정책이 공개 배포를 막으면 임의의 다른 호스팅으로 바꾸지 말고 FT를 부른다.
2. **같은 Sites 프로젝트 사용**
   - `site/.openai/hosting.json`에 `project_id`가 있으면 재사용한다.
   - 없을 때만 사이트를 한 번 생성하고 파일을 보존한다. 프로젝트 ID는 비밀키가 아니지만 임의로 바꾸지 않는다.
3. **공개 승인과 게시**
   - 공개범위 선택을 다시 묻지 않는다. 캠프 정책은 `public` 고정이다.
   - 다만 외부 공개 작업 직전에 *"이 검증본을 누구나 로그인 없이 보는 공개 사이트로 게시할까요?"*라고 한 번 승인받는다.
   - 승인되면 `sites-hosting`의 공개 게시 절차로 **검증된 소스 그대로** 같은 프로젝트에 게시한다. `.openai/hosting.json`에 임의의 접근 설정을 추가하지 않는다.
   - 승인이 없으면 공개하지 않고 현재 상태와 다음 행동만 알린다. `public` 대신 비공개로 임의 배포하지 않는다.
4. **로그아웃 접근 검증**
   - 로그인 정보가 없는 새 브라우저 또는 HTTP 조회로 URL을 연다.
   - 서비스의 고유 제목과 공개 데모가 보이고 `Sign in required`·`Continue with ChatGPT`·`signin-with-chatgpt`가 보이지 않아야 한다.
   - 핵심 입력→버튼→결과 흐름을 실제로 실행한다.
5. **휴대폰 검증**
   - 팀 전원이 자기 폰에서 같은 URL을 연다.
   - 가로 넘침·잘린 버튼·사라진 데이터가 없는지 보고 핵심 기능을 한 번씩 실행한다.
6. **선택한 구현 검증**
   - 정적 방식은 공개 URL의 핵심 입력→결과가 기준선과 같은지 확인한다.
   - 동적 방식은 `context.md`에 합의한 동적 기능을 실제로 실행한다. 저장 기능이면 새로고침 뒤에도 유지되는지, 서버 API면 실제 응답과 오류 폴백이 모두 작동하는지처럼 **그 팀의 기능에 맞는 증거**를 남긴다.

## 완료 판정

`context.md`의 `산출물`에 다음 증거를 남긴다.

```markdown
- 프로토타입: prototype.html
- 배포 방식: 정적 원본 보존 | 동적 앱
- Sites 소스: site/
- 배포:
  - 상태: 공개 배포됨
  - URL: https://…
  - 공개범위: public
  - 기준선 SHA-256: …
  - 동적 전환 이유: 해당 없음 | (이유)
  - 기준선 검증: 바이트 일치 | 제품 계약 확인·의도된 차이 기록
  - 의도된 차이: 없음 | (변경과 이유)
  - 배포 기능 검증: (핵심 기능과 실제 결과)
  - 외부 의존 폴백: 해당 없음 | (실패 조건과 폴백 결과)
  - 로그아웃 접근: 확인
  - 휴대폰 확인: 3/3명
```

아래 중 하나라도 빠지면 URL이 있어도 공개 배포 완료가 아니다.

- `프로토타입`·`배포 방식`·`Sites 소스`
- `기준선 SHA-256`·`동적 전환 이유`·`의도된 차이`
- `public` 공개범위
- 방식에 맞는 기준선 검증
- 선택한 구현의 핵심 기능 검증과 필요한 외부 의존 폴백
- 로그인 없는 공개 데모 접근
- 팀 전원의 휴대폰 핵심 기능 확인

## 재배포

- **정적 방식:** `prototype.html` 수정 → 배포용 복사 → 바이트 일치 확인 → 같은 프로젝트 재배포.
- **동적 방식:** `site/` 앱 소스 수정 → 제품 계약·의도된 차이 확인 → 같은 프로젝트 재배포.

두 방식 모두 새 URL을 만들지 않고 공개 접근과 핵심 기능을 다시 확인한다.

## 안 되면 — 로컬 폴백

1. 5분 안에 해결이 안 보이면 FT를 부른다.
2. 정적 방식은 다른 사람 노트북에서 `prototype.html`의 핵심 기능을 확인한다.
3. 동적 방식은 로컬 앱에서 합의한 동적 기능과 외부 의존 폴백을 실제로 검증한 뒤, 다른 사람 노트북에서 `prototype.html` 기준선도 발표 백업으로 확인한다. 기준선만 열어본 것은 동적 기능 완료 증거가 아니다.
4. 선택한 `배포 방식`은 유지하고 `context.md`에 아래 구조로 적는다.

   ```markdown
   - 프로토타입: prototype.html
   - 배포 방식: 정적 원본 보존 | 동적 앱
   - Sites 소스: site/ | 해당 없음
   - 배포:
     - 상태: 로컬 폴백 검증됨
     - URL: 해당 없음
     - 공개범위: 해당 없음
     - 기준선 SHA-256: …
     - 동적 전환 이유: 해당 없음 | (이유)
     - 기준선 검증: 다른 사람 기기 검증
     - 의도된 차이: 없음 | (동적 앱의 변경과 이유)
     - 배포 기능 검증: (정적 핵심 기능 | 로컬 동적 기능과 실제 결과)
     - 외부 의존 폴백: 해당 없음 | (실패 조건과 폴백 결과)
     - 로그아웃 접근: 해당 없음
     - 휴대폰 확인: 다른 사람 노트북 확인
   ```

   공개 실패 이유는 `로그`에 남긴다.
5. 발표는 로컬 기준선으로 계속 준비하고, 여유가 생기면 같은 `site/` 프로젝트로 재시도한다.

자기 노트북에서만 열어본 것은 `로컬 폴백 검증됨`이 아니다.
