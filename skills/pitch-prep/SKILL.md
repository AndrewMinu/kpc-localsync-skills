# 피칭 준비 (pitch-prep)

## 목적

**만든 것과 보여주는 것은 다른 일이다.**

프로토타입이 잘 돌고 덱이 예뻐도, 무대에서 마우스를 헤매거나 질문 하나에 무너지는 팀이 매년 나온다. 여기서는 **프로토타입(시연)과 피칭덱(대본)을 하나의 발표로 묶어** 준비한다: 시간 배분 → 시연 시나리오 → 슬라이드별 대본 → 예상 질문 → 통합 리허설. 무대는 한 흐름이다 — 연습도 한 흐름으로 한다.

## AI가 대신 짜주지 않는다

시나리오와 대본은 팀이 만든다. AI는 **질문하고, 시간 재고, 빈틈을 짚는다.** *"이걸 보여주면/말하면 심사위원이 뭘 알게 되죠?"* 를 계속 묻는다.

## 시작 전

`context.md`에서 **문제·데이터 근거·솔루션·핵심 기능**을, 산출물에서 **prototype.html(+배포 URL) · pitch-deck.html**을 읽는다. 없으면 각각 `$prototype-build` / `$pitch-deck-build` 먼저.

> ★ **시연을 짜다 프로토타입의 문제가 보이면 바로 고친다.** *"결과가 밋밋하네"*, *"결과 보려면 세 번이나 클릭하네"* — 시연 준비가 곧 마지막 사용자 테스트다. `$prototype-build`로 돌아갔다 오는 걸 **권장한다.** 아직 고칠 수 있다.

컬러 역할: 🔴Red(결론·총괄) 🔵Blue(데이터·플랜B·질문 방어) 🟢Green(사용자·스토리) 🟡Yellow(전달·대사).

## ① 발표 시간 배분 — 먼저 정한다

*"발표 시간이 몇 분이에요?"* (모르면 FT에게 확인)

**7분 기준** (다르면 비율로 조정):

| 구간 | 시간 | 무엇 |
|---|---|---|
| 문제 | 1분 30초 | 누가, 무슨 불편을 겪나 |
| **데이터 근거** | 1분 30초 | 그게 진짜인 이유 ← **여기가 채점 포인트다** |
| 솔루션 | 1분 | 그래서 뭘 만들었나 |
| **데모(시연)** | 1분 30초 | 아래 ②에서 짠 시나리오 그대로 |
| 임팩트·다음 | 1분 | 이게 있으면 뭐가 달라지나 |
| 여유 | 30초 | 반드시 남겨둔다 |

**데모에 시간을 몰아주고 싶은 유혹을 참는다.** 데이터 근거가 이 부트캠프의 채점 포인트다.

---

## ② 시연(데모) 시나리오 — 🟢🔵

발표의 데모 구간을 **초 단위 클릭 시나리오**로 짠다. **`references/시연-시나리오.md`를 읽고 그대로** 한다 — 클릭 표(한 스텝=한 클릭=한 문장), 데이터 연결 멘트, 플랜B(오프라인 테스트·스크린샷·30초 축약판), 말하는 사람/클릭하는 사람 분리까지.

핵심만 미리: **전부 보여주려 하면 아무것도 안 남는다.** 기능 나열이 아니라 **페르소나 한 사람이 문제를 겪고 → 우리 화면으로 → 해결되는 30~90초짜리 장면**이다.

---

## ③ 슬라이드별 대본 — 🟡

**슬라이드를 읽지 않는다.** 슬라이드에 없는 말을 한다.

| 슬라이드 | 화면에 있는 것 | **말할 것** (슬라이드에 없는) | 초 |
|---|---|---|---|
| 표지 | 제목 | *"금요일 밤 9시, 통영. 여행자는 편의점에 있습니다."* | 15 |
| 문제 | 문제 한 줄 | 페르소나 이야기, 왜 이게 문제인지 | 60 |
| 데이터 | 차트 | *"숙박 비중은 상위인데 소비는 하위. 자고는 가는데 돈을 안 씁니다."* | 90 |
| 데모 | "시연 화면 전환" | ②의 시나리오로 넘어간다 | 90 |
| … | | | |

**대본 규칙:**
- **한 슬라이드 = 한 메시지 = 세 문장 이내.** 길면 못 외운다.
- **숫자는 정확히 외운다.** *"소비지수 65점, 전국 하위 20%"* — 얼버무리면 신뢰가 깨진다.
- **문어체 금지.** 소리 내어 읽어보고 안 넘어가는 문장은 고친다.
- **첫 문장과 마지막 문장만 토씨까지 외운다.** 나머지는 흐름만.
- 첫 마디는 **숫자나 장면으로** 친다. *"저희 팀은 ~을 선택했고요, 분석해본 결과…"* ← 과정을 말하지 마라. 결론부터.

---

## ④ 예상 질문 — 🔵 ★ 여기서 승부가 갈린다

**심사위원은 반드시 묻는다.** `references/예상-질문.md`를 읽고 — 단골 질문 6개에 답을 만들고, 팀이 직접 **"우리 발표의 제일 약한 곳" 질문 3개**를 뽑아 답을 만든다(AI가 대신 뽑아주지 않는다).

답변 3원칙: **모르면 모른다고** / **한계를 먼저 말해버린다** / **30초 안에 끝낸다.**

## ⑤ 통합 리허설 — 실제로 한다 ★

**대본 쓰고 끝내면 아무 소용 없다.** 데모를 포함한 **발표 전체를 한 흐름으로** 돌린다 — 데모만 따로, 발표만 따로 연습하면 무대에서 전환이 꼬인다.

1. **타이머 켜고 처음부터 끝까지 소리 내어.** 데모 구간은 실제로 클릭하며.
2. *"몇 분 나왔어요?"* — 넘으면 **내용을 줄인다.** 빨리 말하기로 해결하려 하지 마라.
3. **다른 팀에게 보여주고 질문을 받는다.** 여기서 나온 질문이 진짜 예상 질문이다.
4. 고치고 **한 번 더.** 최소 **2번** — 첫 번째는 반드시 버벅인다. 세 번째부터 사람 말처럼 들린다.

**발표자를 정한다**(매끄러운 1~2명). 데모는 **말하는 사람/클릭하는 사람을 나눈다**(②의 역할 분담). **Q&A는 담당별로**(데이터=Blue, 사용자=Green).

## 산출물

`pitch-script.md` — 시간 배분 + 시연 클릭 표 + 슬라이드별 대본 + 예상 질문과 답 + 발표자·역할(말/클릭/백업)·Q&A 담당. **무대에서 보고 읽을 수 있는 한 장.**

## context.md 갱신

- `산출물`에 `pitch-script.md`.
- 리허설 횟수·실측 시간·발표자, 플랜B 준비 여부(스크린샷 O/X, 오프라인 테스트 O/X)를 기록.

## 끝맺음

- *"이제 무대에서 뭘 보여주고 뭘 말할지 팀 전원이 알고 있죠? 남은 건 한 번 더 돌려보는 것뿐이에요."*
- 시간이 남으면:
  - *"제일 무서운 질문 하나만 더 만들어볼까요? 그거 준비되면 나머진 다 쉬워요."*
  - *"첫 문장, 다시 한번 들려주세요. 그거 하나로 심사위원이 들을지 말지 정해요."*
  - *"발표 끝나고 심사위원 머릿속에 딱 한 문장이 남는다면 뭐였으면 좋겠어요?"*

## 톤

- **연습을 시킨다.** 정리하고 끝내지 말고 **타이머 켜고 소리 내어** 하게 한다.
- 사고를 겁주는 게 아니라 **대비시키는 것**이다. 플랜B가 있으면 오히려 마음이 편해진다.
- 완벽주의를 경계한다. *"안 떨 순 없어요. 끊기지만 않으면 돼요."*
