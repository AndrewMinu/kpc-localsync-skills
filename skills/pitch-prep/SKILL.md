# 피칭 준비 (pitch-prep)

> 문장부호: 출력에 `—`(em-dash)를 쓰지 않는다. 쉼표나 마침표로 끊는다.

## 목적

**만든 것과 보여주는 것은 다른 일이다.**

프로토타입이 잘 돌고 덱이 예뻐도, 무대에서 마우스를 헤매거나 질문 하나에 무너지는 팀이 매년 나온다. 여기서는 **프로토타입(시연)과 피칭덱(대본)을 하나의 발표로 묶어** 준비한다: 시간 배분 → 시연 시나리오 → 슬라이드별 대본 → 예상 질문 → 통합 리허설. 무대는 한 흐름이다. 연습도 한 흐름으로 한다.

## 이 단계의 역할
**전원이 주도한다.** 발표는 한 명이 다 하지 않는다. **각자 최소 한 장씩 말한다.**

컬러 역할: 🔴Red(결론·총괄·전달) 🔵Blue(데이터·플랜B·질문 방어) 🟢Green(사용자·스토리).

`context.md`의 `팀원`을 읽고 이름으로 배분한다. 기본 배치는 이렇게 시작하되 팀이 바꿔도 된다:
🟢 Green = 문제(1~2장) · 🔵 Blue = 데이터(3장)와 *"데이터 근거는?"* Q&A ·
🔴 Red = 데모 시연(5장) + 오프닝·클로징. 2인 팀이면 Red 몫을 둘이 나눈다.

> *"발표자 한 명만 정하면 편하죠. 근데 심사위원은 '이 팀이 같이 했나'를 봅니다.
> 그리고 Q&A는 어차피 답할 사람이 답해야 해요."*

## AI가 대신 짜주지 않는다

시나리오와 대본은 팀이 만든다. AI는 **질문하고, 시간 재고, 빈틈을 짚는다.** *"이걸 보여주면/말하면 심사위원이 뭘 알게 되죠?"* 를 계속 묻는다.

## 시작 전

`context.md`에서 **문제·데이터 근거·솔루션·핵심 기능**을, 산출물에서 **prototype.html 기준선 · 배포 방식 · pitch-deck.html · 배포 증거**를 읽는다. 없으면 각각 `$prototype-build` / `$pitch-deck-build` 먼저.

- `배포 > 상태: 공개 배포됨`이면 `프로토타입`·`배포 방식`·`Sites 소스`와 유효한 `URL`, `공개범위: public`, `기준선 SHA-256`, `동적 전환 이유`, 방식별 `기준선 검증`, `의도된 차이`, `배포 기능 검증`, `외부 의존 폴백`, `로그아웃 접근: 확인`, `휴대폰 확인: N/N명`을 모두 확인한다.
- `배포 > 상태: 로컬 폴백 검증됨`이면 `프로토타입`·`배포 방식`·`Sites 소스`와 `URL: 해당 없음`, `공개범위: 해당 없음`, `기준선 SHA-256`, `동적 전환 이유`, `기준선 검증: 다른 사람 기기 검증`, `의도된 차이`, `배포 기능 검증`, `외부 의존 폴백`, `로그아웃 접근: 해당 없음`, `휴대폰 확인: 다른 사람 노트북 확인`을 확인한다. 동적 앱이면 `배포 기능 검증`과 `외부 의존 폴백`에 로컬 동적 기능의 실제 결과도 확인한다.
- 필요한 증거가 하나라도 없으면 `$prototype-build`로 돌아가 검증부터 마친다.

- `정적 원본 보존` 방식이면 시연 중 수정할 원본은 `prototype.html`이다. 배포용 복사본을 직접 고치지 않는다.
- `동적 앱` 방식이면 수정할 원본은 `site/` 앱 소스다. 빌드 산출물을 직접 고치지 않고, `prototype.html`은 오프라인 폴백으로 유지한다. 기준선과 달라지는 내용은 `context.md`의 `산출물 > 배포 > 의도된 차이`에 남긴다.
- 배포 상태가 `로컬 폴백 검증됨`이면 정적 방식은 기준선을, 동적 방식은 로컬 앱의 동적 기능과 기준선 발표 백업을 각각 다시 확인한다.

> ★ **시연을 짜다 프로토타입의 문제가 보이면 바로 고친다.** *"결과가 밋밋하네"*, *"결과 보려면 세 번이나 클릭하네"* 시연 준비가 곧 마지막 사용자 테스트다. `$prototype-build`로 돌아갔다 오는 걸 **권장한다.** 아직 고칠 수 있다.

## ① 발표 시간 배분: 먼저 정한다

**`context.md`의 `발표 > 제한시간`을 읽는다.** 이게 유일한 기준값이다.

> ⚠ **비어 있으면 여기서 멈춘다.** *"발표 제한시간이 몇 분인지 FT에게 확인하고 오세요. 그거 없이
> 배분을 짜면 나중에 다 다시 짜야 해요."* 확인해 오면 `context.md`에 적고 진행한다.
> **AI가 임의로 정하지 않는다.**

배분은 그 값에서 **비율로** 만든다:

| 구간 | 비율 | 무엇 |
|---|---|---|
| 문제 | 21% | 누가, 무슨 불편을 겪나 |
| **데이터 근거** | 21% | 그게 진짜인 이유 ← **여기가 채점 포인트다** |
| 솔루션 | 15% | 그래서 뭘 만들었나 |
| **데모(시연)** | 21% | 아래 ②에서 짠 시나리오 그대로 |
| 임팩트·다음 | 15% | 이게 있으면 뭐가 달라지나 |
| 여유 | 7% | 반드시 남겨둔다 |

**2026-08 회차는 6분이다** → **1:15 / 1:15 / 0:55 / 1:15 / 0:55 / 0:25**. 이 값을 팀에게 그대로 보여준다.
(다른 값이면: 7분 = 1:30 / 1:30 / 1:03 / 1:30 / 1:03 / 0:24, 5분 = 1:03 / 1:03 / 0:45 / 1:03 / 0:45 / 0:21)

**6분은 생각보다 짧다.** 슬라이드 7장이면 장당 50초고, 그중 데모에 1:15을 떼주면 나머지는 더 준다.
*"6분이에요. 지금 넣으려는 것 중에 뭘 뺄까요?"* 이 질문을 **대본 쓰기 전에** 한 번 하고 시작한다.

**데모에 시간을 몰아주고 싶은 유혹을 참는다.** 데이터 근거가 이 부트캠프의 채점 포인트다.

## ② 시연(데모) 시나리오: 🟢🔵

발표의 데모 구간을 **초 단위 클릭 시나리오**로 짠다. **`references/시연-시나리오.md`를 읽고 그대로** 한다. 클릭 표(한 스텝=한 클릭=한 문장), 데이터 연결 멘트, 플랜B(오프라인 테스트·스크린샷·30초 축약판), 말하는 사람/클릭하는 사람 분리까지.

핵심만 미리: **전부 보여주려 하면 아무것도 안 남는다.** 기능 나열이 아니라 **페르소나 한 사람이 문제를 겪고 → 우리 화면으로 → 해결되는 30~90초짜리 장면**이다.

## ③ 슬라이드별 대본: 🔴

**슬라이드를 읽지 않는다.** 슬라이드에 없는 말을 한다.

> **행은 `pitch-deck.html`의 실제 슬라이드에서 가져온다.** 팀이 6비트에 요소를 얹었거나(B) 직접 짰다면(C)
> 그 뼈대 그대로 쓴다. 아래 표는 기본형(A) 예시일 뿐이니 여기에 맞추려고 슬라이드를 고치지 않는다.
> 초는 ①의 비율에서 나누되, **얹은 장이 있으면 그만큼 다른 데서 뺀다.** 합계가 제한시간을 넘으면 거기서 멈춘다.

| 비트 | 화면에 있는 것 | **말할 것** (슬라이드에 없는) | 초 |
|---|---|---|---|
| One-liner | 제목 | *"금요일 밤 9시, 통영. 여행자는 편의점에 있습니다. 저희는 반려인을 위한 저녁 동선을 만듭니다."* | 15 |
| Problem | 문제 한 줄 | 페르소나 이야기, 그 사람이 포기하는 순간 | 60 |
| Insight | 차트 | *"저희도 잘 곳이 없어서인 줄 알았어요. 숙박 비중은 오히려 상위인데 소비가 하위더라고요. 자고는 가는데 돈을 안 씁니다."* | 90 |
| Product | 구조 한 줄 | 왜 이 방식인지, 뭘 버렸는지, AI가 맡은 판단 | 50 |
| Demo | 서비스 이름 한 줄 | *"이제 직접 보여드리겠습니다."* → ②의 시나리오로 | 75 |
| The Ask | 필요한 것 | *"○○재단과 한 달만 붙여주시면 실제 이용 데이터를 받아보고 싶습니다."* | 50 |

**대본 규칙:**
- **한 슬라이드 = 한 메시지 = 세 문장 이내.** 길면 못 외운다.
- **숫자는 정확히 외운다.** *"소비지수 65점, 전국 하위 20%"* 얼버무리면 신뢰가 깨진다.
- **문어체 금지.** 소리 내어 읽어보고 안 넘어가는 문장은 고친다.
- **파일명·작업 용어를 무대에 올리지 않는다.** 우리끼리 쓰는 말이 관객 귀에 가면 갑자기 과제 발표가 된다.
  화면에 뜨는 글자도 같다. `시연 화면 전환`, `prototype.html`, `MVP 정의서` 같은 라벨을 슬라이드에 남기지 않는다.

  | 우리끼리 | 무대에서 |
  |---|---|
  | *"이제 `prototype.html`로 전환합니다"* | *"이제 직접 보여드리겠습니다"* |
  | *"MVP 정의서에 따르면"* | *"저희가 딱 하나만 고른 기능이"* |
  | *"4단계 데이터 검증 결과"* | *"실제 수치를 받아보니"* |
  | *"프로토타입을 배포했습니다"* | *"지금 이 자리에서 폰으로 열어보실 수 있습니다"* |
- **첫 문장과 마지막 문장만 토씨까지 외운다.** 나머지는 흐름만.
- 첫 마디는 **숫자나 장면으로** 친다. *"저희 팀은 ~을 선택했고요, 분석해본 결과…"* ← 과정을 말하지 마라. 결론부터.
- **첫 15초 안에 "뭘 만들었는지"가 나와야 한다.** 데모데이에서 가장 흔한 실패는 1분이 지나도
  무슨 팀인지 모르겠는 발표다. 장면으로 열되 **한 문장 안에 제품을 붙인다.**
- **마지막은 Ask로 닫는다.** *"감사합니다"* 로 끝내지 않는다. 뭐가 필요한지 말하고 인사한다.

## ④ 예상 질문: 🔵 ★ 여기서 승부가 갈린다

**심사위원은 반드시 묻는다.** `references/예상-질문.md`를 읽고, 단골 질문 6개에 답을 만들고, 팀이 직접 **"우리 발표의 제일 약한 곳" 질문 3개**를 뽑아 답을 만든다(AI가 대신 뽑아주지 않는다).

답변 3원칙: **모르면 모른다고** / **한계를 먼저 말해버린다** / **30초 안에 끝낸다.**

## ⑤ 통합 리허설: 실제로 한다 ★

**대본 쓰고 끝내면 아무 소용 없다.** 데모를 포함한 **발표 전체를 한 흐름으로** 돌린다. 데모만 따로, 발표만 따로 연습하면 무대에서 전환이 꼬인다.

1. **타이머 켜고 처음부터 끝까지 소리 내어.** 데모 구간은 실제로 클릭하며.
2. *"몇 분 나왔어요?"* 넘으면 **내용을 줄인다.** 빨리 말하기로 해결하려 하지 마라.
3. **다른 팀에게 보여주고 질문을 받는다.** 여기서 나온 질문이 진짜 예상 질문이다.
4. 고치고 **한 번 더.** 최소 **2번**: 첫 번째는 반드시 버벅인다. 세 번째부터 사람 말처럼 들린다.

**구간별 담당을 정한다**. 위 ①의 6구간을 나눠 맡아 **전원이 최소 한 장씩 말한다**(위 "전원이 주도한다"). 데모는 **말하는 사람/클릭하는 사람을 나눈다**(②의 역할 분담). **Q&A는 담당별로 나눠 받는다**(데이터=🔵Blue · 사용자=🟢Green · 총괄=🔴Red).

## 끝맺음

- *"이제 무대에서 뭘 보여주고 뭘 말할지 팀 전원이 알고 있죠? 남은 건 한 번 더 돌려보는 것뿐이에요."*
- 시간이 남으면:
  - *"제일 무서운 질문 하나만 더 만들어볼까요? 그거 준비되면 나머진 다 쉬워요."*
  - *"첫 문장, 다시 한번 들려주세요. 그거 하나로 심사위원이 들을지 말지 정해요."*
  - *"발표 끝나고 심사위원 머릿속에 딱 한 문장이 남는다면 뭐였으면 좋겠어요?"*

## 톤

- **연습을 시킨다.** 정리하고 끝내지 말고 **타이머 켜고 소리 내어** 하게 한다.
- 사고를 겁주는 게 아니라 **대비시키는 것**이다. 플랜B가 있으면 오히려 마음이 편해진다.
- 완벽주의를 경계한다. *"안 떨 순 없어요. 끊기지만 않으면 돼요."*
