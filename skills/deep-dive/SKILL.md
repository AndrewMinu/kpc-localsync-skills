# 딥다이브 — 리서치 블록 (deep-dive)

## 목적
주제·지역·데이터만으로는 얕은 아이디어가 나온다. **실제 사용자와 현장의 결**을 팀이 직접 파서 솔루션을 뾰족하게 만든다. 정해진 순서 없이 **필요할 때 끼워 넣는** 선택 활동(주로 2단계 지역 후 ~ 5단계 아이디어 전, 또는 프로토타입 사용자 테스트 때).

## 언제 쓰나
- 아이디어가 뻔하거나 팀 의견이 갈릴 때
- "우리 사용자가 진짜 저럴까?"가 궁금할 때
- 시간이 남아 더 파고들고 싶을 때(2박3일 깊이 채우기)

## 세 가지 활동 (골라서, 퍼실리테이션)

### A. 사용자 인터뷰 (가장 강력)
- **대상 정하기**: *"우리 사용자에 가까운 사람이 주변/현장에 누가 있어요?"* (다른 팀·행인·지역민·본인 경험)
- **질문 설계(스킬이 도움)**: 해결책이 아니라 **경험·불편**을 묻는 5문항. 예: "최근 그 여행 어땠어요? 가장 불편했던 순간은? 그때 어떻게 했어요? 뭐가 있었으면 했어요?"
- **금지**: "이런 앱 있으면 쓸래요?"(유도질문). 대신 과거 행동을 묻는다.
- **정리**: 팀이 각자 인터뷰 → 인상적인 말(원문 인용)·반복되는 불편을 모은다.

### B. 사용자 여정 매핑
- 사용자의 여행을 **단계로 쪼갠다**: 오기 전 → 도착 → 낮 → 저녁 → 숙박 → 다음날 → 귀가.
- 각 단계에 **감정(😀/😐/😫)·행동·불편**을 적는다. *"어느 칸이 제일 나빠요? 왜요?"*
- **가장 나쁜 칸 = 기회.** 우리 솔루션이 그 칸을 겨냥하는지 확인.

### C. 유사사례 조사
- 다른 지역/서비스는 이 문제를 어떻게 풀었나 2~3개 찾기(웹).
- *"걔네는 뭘 잘했고 뭘 놓쳤어요? 우리는 뭘 다르게?"* → 차별점 벼리기.
- 베끼지 않기 — 우리 지역·데이터에 맞게 변형.

## 데이터와 잇기
리서치에서 나온 가설을 **4단계 데이터 검증으로 확인**하게 연결한다("인터뷰에서 '잘 데가 없다'가 많았는데, 숙박 수치로 확인해볼까요?").

## context.md 갱신
- `데이터 검증 요약` 아래 또는 `아이디어`에 **리서치 발견**(핵심 인용·여정의 최악 지점·차별점)을 팀 언어로 기록.
- 로그에 "deep-dive: 무엇을 알게 됨" 추가.

## 끝맺음

## 톤

- 인용·구체 사례를 남기면 발표 설득력이 커진다.
